# Identity and company verification — 2026-11-09

Scope: R05 session authentication, trusted company access and explicit local provisioning. Source base: 3d1275f plus the reviewed R05 change. Customer/payment operations, demo entry and the login UI are not implemented by this stage.

## Implemented behavior

| Route | Behavior |
|---|---|
| GET /api/v1/auth/csrf | Returns token/header/parameter names and establishes an anonymous session when needed |
| POST /api/v1/auth/login | Normalizes email, verifies the versioned PBKDF2 hash, rotates session ID and clears the old CSRF token |
| GET /api/v1/auth/me | Returns the current user/company without credentials, hashes or session identifiers |
| POST /api/v1/auth/logout | Requires current session/CSRF and invalidates the persisted session |
| GET /api/v1/company | Derives company exclusively from the authenticated server principal |

Company and identity facades expose immutable views; JPA entities remain internal. Company locking requires an existing transaction and revalidates expiry after acquiring the PostgreSQL row lock. The server samples Clock once to derive company creation and demo expiry; NewCompany no longer accepts caller-supplied expiry. This internal refinement leaves HTTP schemas unchanged.

Local provisioning requires the local-bootstrap profile, explicit enablement and supplied environment values. It runs without a web server and exits after the transaction. Normal application startup does not create an account. A duplicate normalized email refuses provisioning and rolls back the new company; it never resets or adopts an existing operator. The unique database constraint arbitrates concurrent invocations using INSERT ON CONFLICT DO NOTHING, avoiding an expected SQL exception and its data-bearing log.

## Limits

Official framework references consulted for this implementation: [Spring Security7.0 session management](https://docs.spring.io/spring-security/reference/7.0/servlet/authentication/session-management.html), [CSRF](https://docs.spring.io/spring-security/reference/7.0/servlet/exploits/csrf.html) and [password storage](https://docs.spring.io/spring-security/reference/7.0/features/authentication/password-storage.html). Actual resolved framework versions and integration tests, rather than a generic newer reference example, determined compatibility.

Secure cookie configuration was verified in a production-profile integration context; real public HTTPS/TLS deployment was not tested. Browser validation used a fresh isolated context and native fetch against the actual same-origin API, not a completed login screen. No complete security audit, remote CI run, performance benchmark or production readiness is claimed. Customer/payment/demo workflows and frontend session/cache handling remain their later roadmap tasks.
